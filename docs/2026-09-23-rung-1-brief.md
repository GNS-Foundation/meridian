# Meridian rung-1 — an SDK drafter inside the proven governed path (BRIEF)

**Status:** brief / design, **designed not built — no Meridian code.** **Date:** 2026-09-23.
**Repo/owner:** `meridian-sim` = **`GNS-Foundation/meridian`** (public — an earlier note had it
private; confirmed public via `gh repo view` 2026-09-23).

Rung-1 is the first rung of putting a **real model-driven agent** (Claude Agent SDK) into the governed
loop, using B3's proven `sanctions_hit` disposition path (eu-governed-agent #44, staging-proven) as
the governance substrate. The model **drafts**; the governance — the analyst's signature and the
offline-verifiable two-actor record — stays **outside the model's reach**.

## 1. Drafter-in, governance-out
B3's disposition path is model-agnostic (see `eu-governed-agent/b3-slice/docs/DEMO-RUNBOOK.md`):
draft → §1-A validate → analyst sign → `POST /v1/dispositions` → 201 → GET → offline verify. Only the
**draft** step is model-touchable. Rung-1 swaps the deterministic drafter for a Claude Agent SDK
drafter that, given an alert, produces the `recommendation` + rationale (committed as `rationale_digest`)
and the §1-A `content_body`. Everything downstream is byte-identical:

- The model **never signs and never submits.** The analyst's self-custodied Layer-2 signature and the
  runtime's issuer counter-signature are out-of-band; the model **cannot self-approve**.
- The product-side §1-A validator still runs before signing, so a malformed model draft is caught
  (the runtime treats `content_body` as opaque).
- The persisted record still verifies offline with two signatures — a real model's output is governed.

## 2. Sandboxing the drafter — Claude Agent SDK (API names verified 2026-09-23)
The drafter runs with its tool surface locked so it can only draft (read/analyze), never sign/submit/
mutate. Mechanisms, with exact current identifiers (verified against `code.claude.com/docs/en/agent-sdk`):

- **Permission callback** — `can_use_tool` (Python) / `canUseTool` (TypeScript): receives
  `(tool_name, input, context)` and returns allow/deny (+ optional modified input) — Python returns
  `PermissionResultAllow(updated_input=…)` / `PermissionResultDeny(message=…)`, TS returns
  `{behavior:"allow"|"deny", updatedInput?}`. Deny any signing/submitting/mutating tool; allow only
  read/draft. Set via `ClaudeAgentOptions(can_use_tool=…)` / `options.canUseTool`.
  (Doc: `…/agent-sdk/user-input.md`.)
- **Hooks** — `PreToolUse` (block/modify before a call) and `PostToolUse` (inspect/log), registered as
  `hooks={"PreToolUse":[HookMatcher(matcher="…", hooks=[fn])]}`; a `PreToolUse` hook can set
  `permissionDecision: "deny"`. Evaluation priority `deny > defer > ask > allow`.
  (Doc: `…/agent-sdk/hooks.md`.)
- **Declarative allow/deny** — `allowed_tools` / `disallowed_tools` (patterns, e.g. `"Bash(rm *)"`);
  a bare name removes the tool from the model's view. MCP tools are named `mcp__<server>__<tool>`.
  (Doc: `…/agent-sdk/permissions.md`.)

**Net:** the disposition submit and the signing key are **not tools the drafter can reach** —
`disallowed_tools` + a `can_use_tool` deny keep them out; the human path holds the signature. Re-verify
these identifiers at build time (current as of 2026-09-23).

## 3. Per-role identity via additive mint
Each role in the loop (the drafter, and any future role) gets its **own** API key via the **additive**
mint path — `POST /v1/portal/api-keys` (grafomem PR A #49: additive, never rotate):

- The drafter runs under a **distinct, per-role minted key** — its own identity in the governed trail,
  not a shared tenant key.
- **Additive** means adding a role never revokes another role's key (the login-drop/orphan lesson);
  per-key revoke (grafomem #188) retires a role cleanly when it's decommissioned.
- **Scope the minted key to least privilege:** a drafter key needs draft/read scopes, **not**
  `disposition:write` if submission is a separate governed step — so even a compromised drafter key
  cannot submit a disposition. (Confirm the minted role's scope set against the tenant-admin bound.)

## 4. What rung-1 proves (and what it does not)
- **Proves:** a real model, inside the proven path, yields a disposition a human signs and a supervisor
  verifies offline; the model's output is governed and the model cannot approve itself; the drafter's
  actions are attributable to its own key.
- **Does not:** make any accuracy/learning claim (ADR-0009 holds — AML has no native correctness
  signal); change the disposition contract or the runtime; or build the drafter.
